Cold open

The type-checking mess

record_voice_overSay

Let me show you code that works. It ships, it passes tests, and it's going to get worse every single week.

codeCode — live
PaymentProcessor.java
public class PaymentProcessor {
    public void process(String type, double amount) {
        if (type.equals("CREDIT_CARD")) {
            System.out.println("Charging card: $" + amount);
            // charge card logic
        } else if (type.equals("PAYPAL")) {
            System.out.println("Redirecting to PayPal: $" + amount);
            // paypal logic
        } else if (type.equals("BANK_TRANSFER")) {
            System.out.println("Initiating wire transfer: $" + amount);
            // bank logic
        }
    }
}

Already running — this is meant to look like ordinary, shipped code.

record_voice_overSay

This works. Now product wants Apple Pay support.

quizAsk the room

Where do I go to add that?

Expected answer

Add another else-if branch here.

Right — and now imagine this same string, "CREDIT_CARD" and friends, is also checked in the receipt generator, the refund service, the analytics dashboard, and the fraud checker. Five other files, each with their own if/else chain testing the same type string. How many places do you now touch to add Apple Pay?

quizAsk the room

What happens if I typo "CREDIT_CARD" as "CREDIT_CRAD" in one of those five other files?

Expected answer

Nothing throws. The condition is just false, the transaction silently does nothing in that one file, and nobody finds out until a customer complains.

No compiler error, no exception — a plain string comparison that's wrong just quietly does the wrong thing. That's the actual cost of this design, not just the tedium of touching five files.

record_voice_overSay

The core issue: the *type* of a thing knows what it is, but nothing about *how it should behave* lives with the type. Behavior is scattered across whoever happens to check the type string. What if, instead, each payment type carried its own behavior, and the caller just said "process yourself" without caring which kind it is? That's the whole two hours: how do we get there safely, without creating new problems on the way.

Segment 2 · 00:07–00:20

Foundations

Why inheritance exists

record_voice_overSay

Before we can get to "each type carries its own behavior," we need a mechanism for saying "this is a kind of that" and sharing structure between related types. That mechanism is inheritance — and I want to build it properly before I show you where it goes wrong, because you need to see it work first.

codeCode — live
Animal.java
public class Animal {
    protected String name;
    public Animal(String name) { this.name = name; }
    public void eat() { System.out.println(name + " is eating."); }
}
codeCode — live
Dog.java
public class Dog extends Animal {
    public Dog(String name) { super(name); }
    public void bark() { System.out.println(name + " says Woof!"); }
}
quizAsk the room

Dog never redefines eat(). Why does new Dog("Rex").eat() work at all?

Expected answer

It's inherited — a subclass automatically gets every public/protected member of its superclass, without rewriting it.

record_voice_overSay

That's the reuse half of inheritance, and it's real, but it's not the important half — we'll get to the important half in Segment 5. The half to internalize right now is the test for *when it's appropriate at all*: the "is-a" test. Dog IS AN Animal. That's a legitimate hierarchy.

drawBoard / screen
Before you write "extends", ask:
  Is B literally a kind of A?             ("Dog is an Animal" -> yes)
  Will every A-shaped assumption still hold for B?   (Segment 3)
  If it's really "B uses an A" or "B has an A"
    -> that's composition, not inheritance   (Segment 9)
quizAsk the room

Quick gut check: should SavingsAccount extend CheckingAccount? Or should both extend some shared Account?

Expected answer

Both should extend (or implement) a shared Account type. SavingsAccount is not a kind of CheckingAccount — they're siblings, not parent and child.

Common wrong answer

SavingsAccount extends CheckingAccount, since a savings account is kind of like a checking account.

"Kind of like" is doing a lot of work in that sentence, and that's exactly the trap — a vague resemblance isn't the is-a test. Neither is literally a specialization of the other; they're two different specializations of a shared concept. That shared concept is the actual superclass.

Segment 3 · 00:20–00:32

Where it breaks

The Liskov Substitution Principle

record_voice_overSay

Now let's break it, on purpose, with a hierarchy that passes the English "is-a" test perfectly and still causes real bugs.

codeCode — live
Rectangle.java
class Rectangle {
    protected double width, height;
    public void setWidth(double w) { width = w; }
    public void setHeight(double h) { height = h; }
    public double area() { return width * height; }
}
codeCode — live
Square.java
class Square extends Rectangle {
    @Override
    public void setWidth(double w) { width = w; height = w; }
    @Override
    public void setHeight(double h) { width = h; height = h; }
}

Square keeps both sides equal by having each setter update both fields.

quizAsk the room

Mathematically, is a square a rectangle? Given that, this looks like a perfectly reasonable hierarchy. Now: I write a method that takes any Rectangle, calls setWidth(5), then setHeight(10), then asserts area() == 50. Does that assertion still hold if I hand it a Square instead of a plain Rectangle?

Expected answer

No. Square's setHeight(10) also overwrites width to 10, because that's how it keeps itself square. So after both calls, width and height are both 10, and area() is 100, not 50.

Common wrong answer

Yes — a square is still a rectangle, so any Rectangle code should work fine on it.

Walk it through on the board with them, line by line, plugging in Square's overridden setters. The area comes out to 100. Being a rectangle in the mathematical, English sense didn't save the assertion — the code that was correct for every Rectangle is now wrong for this particular subclass.

record_voice_overSay

This is the actual definition of the Liskov Substitution Principle, and it's stricter than "is-a": if S is a subtype of T, you should be able to replace any T with an S, anywhere, without breaking the correctness of code written against T. It's not asking whether the English description fits — it's asking whether the *behavioral contract* callers silently rely on still holds. Rectangle's contract implicitly promises that setWidth doesn't touch height. Square breaks that promise to keep a different promise to itself.

drawBoard / screen
Liskov Substitution Principle:
If S extends T, any code that correctly works with a T
must also work correctly with an S, with no surprises.

"Is-a" in English is necessary, but not sufficient.
The BEHAVIOR has to hold too.
quizAsk the room

Same idea, classic other example: Bird has a fly() method, Penguin extends Bird. What breaks?

Expected answer

Penguins can't fly, so fly() either throws, does nothing, or lies — and any code that calls fly() on a Bird reference now misbehaves the moment that Bird happens to be a Penguin.

helpIf they're stuck

If "behavioral contract" feels too abstract, ground it: contracts aren't just what's written in a method signature — they're the assumptions every caller silently relies on. "width and height are independent after individual setter calls" is one of those unwritten assumptions every piece of code calling Rectangle relies on, even though it's never written down anywhere.

Segment 5 · 00:37–00:57

Polymorphism

Dynamic dispatch fixes the cold open

record_voice_overSay

Now we have the tool to actually fix Segment 1's mess, properly. Instead of one class checking type strings, define what every payment type can *do*.

codeCode — live
PaymentMethod.java
public interface PaymentMethod {
    void process(double amount);
}
codeCode — live
CreditCardPayment.java
public class CreditCardPayment implements PaymentMethod {
    @Override
    public void process(double amount) {
        System.out.println("Charging card: $" + amount);
    }
}
codeCode — live
PayPalPayment.java
public class PayPalPayment implements PaymentMethod {
    @Override
    public void process(double amount) {
        System.out.println("Redirecting to PayPal: $" + amount);
    }
}
codeCode — live
PaymentProcessor.java
public class PaymentProcessor {
    public void process(PaymentMethod method, double amount) {
        method.process(amount);
    }
}

No if, no else, no string. The if/else chain from Segment 1 is just gone.

quizAsk the room

PaymentProcessor's code just says method.process(amount), and method is declared as type PaymentMethod. How does the JVM know which class's process() to actually run?

Expected answer

It looks at the actual runtime type of the object — not the declared/reference type. Every object carries a reference to its real class's method table, and at runtime the JVM looks up process() in *that* table.

Common wrong answer

It runs PaymentMethod's own process() — but PaymentMethod doesn't have a body, so that can't be it either.

Right, PaymentMethod is an interface — there's no default body to fall back to (ignore default methods for a moment, we'll hit those in Segment 7). The lookup happens on whatever concrete object is actually sitting in that variable at that moment, which is why this is called runtime polymorphism — the decision is made at runtime, based on the real object, not at compile time, based on the declared type.

drawBoard / screen
PaymentMethod method = new PayPalPayment();
                ↑                ↑
          declared type      actual (runtime) type

method.process(amount)
  -> JVM looks at the ACTUAL type (PayPalPayment)
  -> runs PayPalPayment's process(), not some generic default
record_voice_overSay

Now add Apple Pay. Watch what I touch.

codeCode — live
ApplePayPayment.java
public class ApplePayPayment implements PaymentMethod {
    @Override
    public void process(double amount) {
        System.out.println("Authorizing via Apple Pay: $" + amount);
    }
}

One new file. PaymentProcessor.java is not open, and doesn't need to be.

quizAsk the room

Is the Segment 1 typo bug — "CREDIT_CRAD" silently doing nothing — possible here?

Expected answer

No. There's no string to typo. You pass an actual PaymentMethod object; if a class doesn't implement process(), it doesn't compile at all.

quizAsk the room

We just added a whole new payment type without editing a single existing, already-tested file. Anyone know what principle that's an example of?

Expected answer

The Open/Closed Principle — open for extension (new subclasses), closed for modification (existing, tested code doesn't change). If nobody has the term, that's fine — just name it and move on, the behavior matters more than the label.

record_voice_overSay

One more thing worth naming, briefly, because you'll see the term elsewhere: this exact shape — swapping behavior in and out through a shared interface — is called the Strategy pattern. We're not doing a design-patterns unit today. Just recognize the shape when you see it; you built it yourself in the last ten minutes.

helpIf they're stuck

If dynamic dispatch still feels like magic, use a mailing analogy: you address a letter to "whoever currently occupies the role of process()" — you don't know at write-time whether that's CreditCardPayment or PayPalPayment, but whoever's actually living there when the letter arrives is who opens it. The JVM resolves "who's actually there" at the moment the call happens, not when the code was written.

Segment 6 · 00:57–01:09

A common mix-up

Overloading vs. overriding

record_voice_overSay

Two words that sound related and get confused constantly: overloading and overriding. Overriding is exactly what we just did in Segment 5 — a subclass provides its own implementation of a method already defined by its supertype, and the runtime decides which version runs based on the actual object. Overloading is a completely different mechanism: multiple methods with the *same name* but *different parameter lists*, and it's resolved at *compile time*, based on the *declared* types of the arguments — nothing about runtime enters into it.

codeCode — live
Calculator.java
public class Calculator {
    public int add(int a, int b) { return a + b; }
    public double add(double a, double b) { return a + b; }
    public int add(int a, int b, int c) { return a + b + c; }
}
quizAsk the room

Which add() runs for calc.add(1, 2)? For calc.add(1.0, 2.0)? For calc.add(1, 2, 3)?

Expected answer

The compiler matches by parameter type and count, at compile time — the int version, the double version, and the three-argument version, respectively. No ambiguity, decided before the program ever runs.

codeCode — live
OverloadTrap.java
public void print(Object obj) { System.out.println("Object version"); }
public void print(String str) { System.out.println("String version"); }

Object o = "hello";
print(o);   // which one runs?

o holds a String at runtime. Ask before revealing the answer.

quizAsk the room

o actually holds a String at runtime. Which print() runs?

Expected answer

The Object version — because overload resolution happens at compile time, based on the *declared* type of the variable (Object), not what it actually holds at runtime.

Common wrong answer

The String version, since that's what o actually is when the line executes.

This is the exact opposite of what Segment 5 taught you about overriding, and mixing the two up is the single most common trip-up in this whole topic. Overriding looks at the real object at runtime. Overloading looks at the declared type at compile time, full stop — it never even glances at what's actually in the variable when the program runs.

drawBoard / screen
OVERRIDING                          OVERLOADING
same signature, subclass            same name, different params
resolved at RUNTIME                 resolved at COMPILE TIME
based on ACTUAL object type         based on DECLARED type of arguments
needs inheritance / an interface    same class, no inheritance needed
@Override annotation recommended    no special annotation
record_voice_overSay

Constructors can be overloaded but never overridden — they aren't inherited at all. And @Override is more than documentation: if you typo a parameter type or name while thinking you're overriding, without @Override the compiler will happily let you create a brand-new, unrelated overload instead — no error, just a method that silently never runs when you expected an override to kick in. With @Override, that same typo becomes a compile error instead of a 2am bug.

helpIf they're stuck

If "resolved by declared type, not actual type" feels backwards right after learning overriding does the opposite, slow down and repeat the board exactly, then rerun the o example: "The compiler doesn't execute your program to decide which print to call — it decides once, while compiling, using only what it can see in the variable's declared type. It has no way of knowing, at compile time, that o will hold a String in every case it might run."

Segment 7 · 01:09–01:25

Abstraction

Why it exists — and when it doesn't earn its keep

record_voice_overSay

Why do we even need PaymentMethod as an interface, if CreditCardPayment and PayPalPayment already work fine as classes on their own? The honest answer isn't "to hide implementation details" — that's encapsulation, and it's a slightly different concern that people reach for as an explanation because it sounds right without actually explaining anything. Abstraction is about depending on *what something does*, not *which concrete type it is* — so the code that depends on it doesn't have to change when a new implementation shows up, or an old one changes.

quizAsk the room

Suppose PaymentProcessor.process() had instead been written to take a CreditCardPayment parameter directly — hardcoded to the concrete class. What has to happen when PayPal support gets added?

Expected answer

PaymentProcessor itself needs a new overloaded method, or a rewrite. The interface is specifically what let PaymentProcessor stay untouched in Segment 5 — that's the entire payoff.

codeCode — live
PaymentMethod.java
public interface PaymentMethod {
    void process(double amount);

    default void logAttempt(double amount) {
        System.out.println("Attempting payment of $" + amount);
    }
}

A default method — Java 8+ lets an interface carry a body, not just a signature.

codeCode — live
PaymentMethodBase.java
public abstract class PaymentMethodBase implements PaymentMethod {
    protected final String transactionId = UUID.randomUUID().toString();

    protected void logCommon() {
        System.out.println("txn=" + transactionId);
    }

    public abstract void process(double amount);
}
record_voice_overSay

Use an interface when you're defining a capability with no shared state — "anything that can process a payment." Use an abstract class when subclasses need to share actual state or a partial implementation, not just a signature — every payment method here needs a transactionId and logCommon(), and an abstract base class avoids retyping that in every subclass. A class can implement many interfaces, but extend only one class — that's as much the practical dividing line as the philosophical one.

record_voice_overSay

One sentence on default methods, since I just used one: if a class implements two interfaces that both define a conflicting default method, Java will not silently pick one for you — it forces you to override and resolve it explicitly. That's the whole diamond-problem story for today; it's a corner case, not core material.

quizAsk the room

If I have exactly one implementation of PaymentMethod today, with no concrete plan for a second, do I still need the interface?

Expected answer

There's no single right answer — that's the point of asking it. If you're confident there will never be a second implementation and you're not defining a testable boundary, an interface here is a layer of indirection with no current payoff. The value of abstraction scales with how much variation or future substitution you actually expect — it isn't a rule to apply everywhere by default.

helpIf they're stuck

If "substitutability, not hiding" isn't landing, return to Segment 1: we can add Apple Pay without touching PaymentProcessor not because we hid CreditCardPayment's internals, but because PaymentProcessor never knew about CreditCardPayment specifically in the first place — it only ever knew the interface. That's the actual value, and it has nothing to do with secrecy.

Live code

Open/closed, proven end to end

record_voice_overSay

Let's build the whole thing end to end and prove the closed-for-modification claim by literally not opening PaymentProcessor.java again.

record_voice_overSay

Add a fourth payment type — BankTransferPayment — same shape as ApplePayPayment. New file only. Then write a test that proves PaymentProcessor is testable without any real payment logic at all, because it only ever depends on the interface shape.

codeCode — live
PaymentProcessorTest.java
class FakePayment implements PaymentMethod {
    boolean called = false;
    public void process(double amount) { called = true; }
}

@Test
void processorCallsProcessOnWhicheverMethodItReceives() {
    FakePayment fake = new FakePayment();
    new PaymentProcessor().process(fake, 100.0);
    assertTrue(fake.called);
}

No real card, no real network call, no mocking framework needed — just an object shaped like the interface.

quizAsk the room

What would this test look like if PaymentProcessor were hardcoded to CreditCardPayment instead of the interface?

Expected answer

You'd need a real CreditCardPayment (or heavy mocking of one), possibly touching real payment logic — much harder to isolate, and the abstraction is exactly what removed that need.

Segment 9 · 01:39–01:51

The other side

Composition over inheritance

record_voice_overSay

Inheritance isn't free. Every subclass is coupled not just to its superclass's public interface, but to its *implementation details* — and that coupling can bite you later, even when you did nothing wrong.

codeCode — live
InstrumentedHashSet.java
class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override
    public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
    }

    public int getAddCount() { return addCount; }
}
quizAsk the room

I call set.addAll(List.of("a", "b", "c")). What's addCount afterward?

Expected answer

It depends on HashSet's internal implementation, and in the real JDK it comes out to 6, not 3.

Common wrong answer

3 — one for each element added.

HashSet's own addAll() is internally implemented by calling add() once per element. So addCount gets bumped once in your overridden addAll (+3), and then again inside each of those three internal calls to your overridden add() (+3 more) — 6 total. The bug isn't in your logic. It's that your subclass quietly assumed *how* addAll() is implemented internally, and that implementation detail was never part of any documented contract — it can even change between JDK versions.

record_voice_overSay

This is the fragile base class problem: a change to a superclass's internal implementation — not its documented contract — can silently break subclasses, because subclasses often end up depending on behavior nobody ever promised to keep stable. The fix: prefer composition. Wrap a HashSet inside your own class instead of extending it, and expose only what you actually want.

codeCode — live
InstrumentedSet.java
class InstrumentedSet<E> {
    private final Set<E> delegate = new HashSet<>();
    private int addCount = 0;

    public boolean add(E e) {
        addCount++;
        return delegate.add(e);
    }

    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return delegate.addAll(c);
    }

    public int getAddCount() { return addCount; }
}

addCount is now exactly what was added — the internals of HashSet are none of this class's business.

drawBoard / screen
"Favor composition over inheritance" (Effective Java, Item 18)

Inheritance:  reuses implementation AND exposes you to
              changes in that implementation's internals

Composition:  reuses through a reference (has-a) — you decide
              exactly which methods you expose, and how
quizAsk the room

Given everything today, is inheritance ever the right call, or should we default to composition always?

Expected answer

Inheritance earns its place when there's a genuine is-a relationship AND you actually need polymorphic substitutability — client code treating many types uniformly through one supertype, the way PaymentProcessor does. Composition is right when you just want to reuse behavior without that substitutability, or when the is-a claim fails Segment 3's Liskov test.

helpIf they're stuck

If the addCount surprise doesn't land from the explanation alone, run it live with a println inside add() — watching it print twice per element for a single addAll() call is more convincing than any diagram.

Segment 10 · 01:51–01:57

Recap

The gotchas, as a checklist

record_voice_overSay

Fast recap, as a list of things that will actually bite you.

  • closeUsing inheritance purely for code reuse — it also inherits every future change to the superclass's internals, whether you want that or not
  • closeTrusting the English "is-a" test alone — Square/Rectangle passes it and still fails Liskov substitution
  • closeConfusing overloading (compile-time, by declared argument type) with overriding (runtime, by actual object type)
  • closeForgetting @Override — a typo'd signature silently becomes a new, unrelated overload instead of a compile error
  • closeCalling an overridable method from a constructor — the subclass's own fields aren't initialized yet when the superclass constructor body runs
  • closeTreating abstraction as "hiding details" instead of "enabling substitution" — substitution is what actually removed the if/else chain
  • closeReaching for an interface before there's a second implementation or a test boundary that needs one — pure overhead until then
record_voice_overSay

If you remember nothing else: the "is-a" test gets you in the door, but Liskov substitution is the real bar. Polymorphism is what let us delete the if/else chain, and it works because callers depend on an interface, not a concrete type — which is the entire point of abstraction. And inheritance is a tool for substitutability, not a default reuse mechanism; when you just want to reuse behavior, composition is usually the safer choice.
