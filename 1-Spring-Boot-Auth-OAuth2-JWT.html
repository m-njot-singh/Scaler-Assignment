Before you teach

How to run this class

How to use this document: SAY is close to word-for-word what you say. BOARD is what goes on the whiteboard/screen at that moment — draw it as you talk, don't pre-draw it. Scope decisions (and why)

This class does not cover password hashing/bcrypt mechanics, CSRF tokens in depth, refresh token rotation strategies, or JWKS key-rotation mechanics in depth. Each is a 20-minute topic on its own — covering them shallowly would add vocabulary without understanding. Where they matter, one sentence names why they exist, so nobody leaves thinking they don't exist, but the deep dive is cut. The one OAuth2 grant type taught in full is Authorization Code + PKCE, because it's the one you'll actually use. Client Credentials gets one paragraph. Implicit and Password grants get one sentence each, explaining why they're dead — teaching a deprecated flow in detail just to say "don't use this" wastes the room's time.

Segment 2 · 00:06–00:16

Foundations

Authentication vs. authorization

record_voice_overSay

Two words that get used interchangeably and shouldn't be. Authentication answers who are you. Authorization answers what are you allowed to do. They are separate questions with separate failure modes, and almost every real-world auth bug is someone solving one and assuming it solved the other.

drawBoard / screen
AUTHENTICATION            AUTHORIZATION
"Who are you?"            "What can you do?"
proving identity          checking permission
happens once (per token)  happens on EVERY request
record_voice_overSay

Concretely: when you log in with a password, that's authentication — you're proving you're the owner of that account. When the server then checks 'is this user an admin' before letting them hit /admin/deleteUser, that's authorization. You can be perfectly authenticated — the server is 100% sure you're user 17 — and still be told no.

quizAsk the room

I'm logged in as a normal user. I try to hit /admin/deleteUser/5. The server says 403 Forbidden. Which of the two — authentication or authorization — just stopped me?

Expected answer

Authorization — you know who I am, you're just saying I can't do that.

Common wrong answer

Authentication, because I got denied.

Denied at what question, though? Nobody's doubting you're user 17. They're doubting you're allowed. If authentication had failed you'd get 401, not 403 — that status code split exists exactly to mark this distinction. 401 means 'I don't know who you are.' 403 means 'I know exactly who you are, and the answer is no.'

record_voice_overSay

Hold onto that 401/403 distinction — it'll matter when we write the actual filter later, because getting it backwards is the single most common bug in a homemade auth layer.

helpIf they're stuck

If the 401/403 question isn't landing, make it concrete: 'If I show up at a bar with a fake ID that doesn't scan, what happens? Now if I show up with my real, valid ID, but I'm 19 — what happens?' First case: they can't authenticate you. Second case: they know exactly who you are and still say no. That's authorization.

Segment 3 · 00:16–00:30

The old way

Session-based auth, and why it stops working

record_voice_overSay

Let's solve authentication the way the web solved it for 20 years, because you need to see it work before you see why it breaks. This is session-based auth, and it's still correct for a lot of apps — a plain server-rendered web app with one backend should probably still use this. Don't walk out of here thinking sessions are wrong. They're wrong for a specific shape of system, which we're about to build.

drawBoard — diagram
sequenceDiagram participant B as Browser participant S as Server participant DB as Session Store B->>S: POST /login (username, password) S->>S: verify password (hash compare) S->>DB: create session { userId: 17 }, get sessionId=abc123 S->>B: Set-Cookie: SESSION=abc123 Note over B: cookie stored, sent automatically on every request B->>S: GET /users/17 (Cookie: SESSION=abc123) S->>DB: look up session abc123 DB->>S: userId=17 S->>B: 200 OK, user data
record_voice_overSay

Login happens once. The server creates a session record — just a row somewhere, sessionId → userId 17 — and hands the browser a cookie containing only the session ID, nothing meaningful on its own. The browser doesn't have to do anything clever; cookies get attached to every request automatically. On every following request, the server takes that ID, looks it up in the session store, and now knows who's asking. Notice: the server is doing a lookup on every single request. That's the detail to remember — we'll come back to it.

record_voice_overSay

This is genuinely fine for a monolith serving a browser. Where does it start to hurt?

quizAsk the room

Say this app gets popular and you now run three instances of this server behind a load balancer, for redundancy. I log in — my request hits instance A, which creates the session in its own memory. My next request gets load-balanced to instance B. Does instance B know who I am?

Expected answer

No — B never saw that session get created.

Common wrong answer

Just add a database for sessions.

Right idea, and that's a real fix — a shared session store like Redis. But notice what you just did: you added a network hop and a shared piece of infrastructure that all three servers now depend on, just to answer 'who is this.' Every request, to every instance, now costs a lookup against something external. That's not free, and it's not the only cost.

record_voice_overSay

Second problem, worse than the first: what if the client isn't a browser at all? A mobile app. A different backend service calling this one. Cookies are a browser convention — nothing about 'session ID in a cookie' means anything to a mobile HTTP client or another server. You can fake it — send the ID as a header instead of a cookie — but you still haven't solved problem one: someone, somewhere, still has to store that session and look it up on every request.

drawBoard / screen
Sessions require:
 1. Server-side storage (shared across instances)
 2. A lookup on every request
 3. A browser (or you're reinventing cookies badly)
record_voice_overSay

So the question that gets us to JWT is: can the token itself carry enough information that the server doesn't need to look anything up? Can 'who you are' travel with the request instead of living in a database the server has to go ask?

helpIf they're stuck

If 'why is a DB lookup bad' doesn't land, make it concrete with numbers: 'If your API does 5,000 requests a second, session-based auth means 5,000 extra reads a second against your session store, forever, just to know who's asking, before you've done any actual work. That store becomes a dependency your entire API is now hostage to.'

Segment 4 · 00:30–00:50

JWT

A token that answers its own questions

record_voice_overSay

A JWT — JSON Web Token — is the answer to 'can the token carry its own proof.' I'm not going to lead with the acronym expansion, because that tells you nothing. Here's the actual idea: what if the server writes down who you are, signs that statement with a secret only the server knows, and hands you the signed statement? You keep it. You show it on every request. The server doesn't need to remember anything — it just re-checks the signature. If the signature is valid, the statement inside must have come from the server, unmodified, because only the server could have produced that signature.

drawBoard / screen
xxxxx.yyyyy.zzzzz
 ↑      ↑      ↑
header payload signature
record_voice_overSay

Three parts, separated by dots. Let's build one by hand conceptually before we touch code.

drawBoard / screen
HEADER  (base64url):  { "alg": "HS256", "typ": "JWT" }
PAYLOAD (base64url):  { "sub": "17", "roles": ["USER"], "iat": 1234, "exp": 1238 }
SIGNATURE:  HMAC-SHA256( base64url(header) + "." + base64url(payload), SECRET_KEY )
record_voice_overSay

Header says how it's signed. Payload — these are called claims — says who and what. sub is subject, the user ID. exp is expiry, as a Unix timestamp — this token is only good for a few minutes, on purpose, and we'll get to why. Then the signature: take the header and payload, glue them together, run them through HMAC-SHA256 with a secret key only the server has, and that output is the signature. Final token is all three pieces, base64url-encoded, joined by dots.

quizAsk the room

Base64 is not encryption, it's just an encoding — like Morse code, not a cipher. Given that, if I hand you a JWT, can you read the payload without knowing the secret key?

Expected answer

Yes — you just base64-decode it, no key needed.

Common wrong answer

No, you need the secret to read it.

Try it: paste any JWT into jwt.io with no secret entered. The payload decodes instantly. The secret is only needed to verify the signature — to check nobody tampered with it — not to read it. This is the single most common JWT misconception, and it has a real consequence: never put anything in a JWT payload you wouldn't be comfortable seeing on a public API response, because that's effectively what it is. No passwords, no secrets, no full SSNs — in claims, in the payload.

quizAsk the room

So — if I, an attacker, base64-decode the payload, change "roles": ["USER"] to "roles": ["ADMIN"], and re-encode it, does that work?

Expected answer

No — the signature won't match anymore.

If someone says yes, walk through it: the signature was computed over the original header+payload bytes. Change one character in the payload and re-run HMAC-SHA256 on the new bytes — you get a completely different signature. You don't have the secret key, so you can't produce the signature the server would accept. The server recomputes the signature on its end from what you sent and compares. Any change, anywhere, and it won't match.

drawBoard / screen
base64 encoding  → reversible by anyone, no key needed   (readable, not secret)
HMAC signature   → provable only by the secret holder    (tamper-evident)

JWT is a signed statement, not a locked box.
record_voice_overSay

Now let's write the code that does this, in order — the way you'd actually build it.

codeCode — live
JwtUtil.java
@Component
public class JwtUtil {

    // In real code this comes from an environment variable / secrets manager,
    // never a literal in source. It's here so you can see the shape.
    private static final Key KEY = Keys.hmacShaKeyFor(
        "replace-with-a-long-random-secret-at-least-32-bytes".getBytes()
    );

    public String generateToken(String userId, List<String> roles) {
        return Jwts.builder()
            .setSubject(userId)
            .claim("roles", roles)
            .setIssuedAt(new Date())
            .setExpiration(new Date(System.currentTimeMillis() + 15 * 60 * 1000)) // 15 min
            .signWith(KEY, SignatureAlgorithm.HS256)
            .compact();
    }
}

Type setExpiration last and pause — this 15-minute number is what the next question is about.

quizAsk the room

Why would you deliberately make this token stop working in 15 minutes, when the whole pitch of JWT was 'the server doesn't have to remember anything'?

Expected answer

Because if it leaks, it's only dangerous for 15 minutes.

If nobody gets there, ask it differently: 'Think about the session version — if someone steals a session cookie, what can you do about it? You go into the session store and delete that row. Session revoked, instantly. Now think about a JWT — the server isn't storing it anywhere. If it leaks, how do you revoke it?' Pause. 'You can't. Not directly. There is no row to delete.' This is the actual cost of statelessness: you traded 'a lookup on every request' for 'I can't kill a token early.' Short expiry is how you contain that. We'll come back to this exact tradeoff in a few minutes.

codeCode — live
JwtUtil.java
    public Claims validateAndParse(String token) {
        return Jwts.parserBuilder()
            .setSigningKey(KEY)
            .build()
            .parseClaimsJws(token)   // throws if signature invalid or token expired
            .getBody();
    }

parseClaimsJws recomputes the signature and checks exp — no database call anywhere in this method.

helpIf they're stuck

If someone's confused about when the server checks the signature vs. when a session lookup happens, draw the two flows side by side: 'Session: every request → ask session store "who is this?" → get answer. JWT: every request → recompute signature myself → already have the answer.' Same question, answered two different ways — one needs a phone call to someone else, one you can answer alone, using math.

Segment 6 · 00:56–01:06

JWT in production

Where JWTs actually go wrong

record_voice_overSay

JWT solves the lookup problem. It does not solve everything, and here's where teams get hurt — three specific places.

drawBoard / screen
1. WHERE DO YOU STORE IT ON THE CLIENT?
2. HOW DO YOU REVOKE IT EARLY?
3. WHAT HAPPENS WHEN IT EXPIRES MID-SESSION?
record_voice_overSay

On a browser, you've got two real options: localStorage, or an httpOnly cookie. localStorage is easy — JavaScript reads and writes it directly — but that's exactly the problem. Any JavaScript running on your page can read it, which means if you have any XSS vulnerability anywhere on your site, the attacker's injected script can just read the token straight out of localStorage and exfiltrate it. An httpOnly cookie can't be read by JavaScript at all, which kills that attack — but cookies get sent automatically by the browser on every request to that domain, which reopens a different door: CSRF, where a malicious site tricks your browser into firing a request to your API using your cookie without you meaning to. There's no answer here that's just 'safe' — it's a tradeoff, and which side you pick depends on what else your app is exposed to. I'm not going to teach CSRF defenses in depth today — that's its own class — but you should leave knowing this is a real decision, not an afterthought.

quizAsk the room

Given that tradeoff, why might a mobile app not care about this argument at all?

Expected answer

No browser, no cookies, no XSS in the browser sense — it just stores the token in secure app storage (Keychain / Keystore) and attaches it as a header itself.

record_voice_overSay

We already hit the revocation problem: there's no row to delete. The practical fix is a pair of tokens — a short-lived access token, the one we've been building, maybe 15 minutes; and a long-lived refresh token, stored more carefully, that the client trades in for a new access token when the old one expires. If something goes wrong, you can't kill an access token that's already out — but you can revoke the refresh token, which stops new access tokens from being minted. Worst case with a leaked access token: 15 minutes of exposure, not forever.

drawBoard / screen
Access token:  short-lived (minutes), sent on every API call
Refresh token: long-lived, stored more carefully, traded in for a new access token
             -> revoking the refresh token stops the bleeding going forward
             -> it does NOT invalidate an access token already issued
quizAsk the room

If your access token is only good for 15 minutes, what happens to someone using your app for 20 minutes straight, if there's no refresh logic?

Expected answer

They get logged out / get a 401 partway through.

Right — so client code needs to catch that 401, use the refresh token to silently get a new access token, and retry, without the user noticing. That retry logic is easy to forget and is exactly the kind of thing that only shows up in production, on the one user session that runs long.

helpIf they're stuck

If the access/refresh split feels abstract, anchor it to something familiar: 'This is exactly why you get logged out of some apps after being idle a while, but staying active keeps you logged in — active use keeps refreshing the access token; idle time means the refresh token itself eventually expires too.'

Segment 7 · 01:06–01:11

Motivation

The delegation problem

record_voice_overSay

Everything so far has been about your server proving its own users' identities. New problem: a travel-booking app wants to read events off your Google Calendar so it can suggest flights around your trip. How does that app prove to Google who you are?

quizAsk the room

Simplest possible answer — what's the naive thing that app could ask you to do?

Expected answer

Give it your Google username and password.

Right — and who's ever actually done that, typed their real Google password into some random third-party app? That's the naive answer, and it's a disaster: now that travel app has your full Google password, forever, with no limits — it could read your email, your Drive, delete your account, anything. You've handed over the master key to look at a calendar.

record_voice_overSay

OAuth2 exists to solve exactly this: 'I want to let a third party access one narrow thing on my behalf, without ever handing them my password, and I want to be able to revoke that access later without changing my password.' That's it. That's the whole problem OAuth2 is for. It is not, itself, a login system — it's a delegation and authorization protocol. Keep that distinction in your pocket; we'll need it in twenty minutes.

Segment 8 · 01:11–01:29

OAuth2

Roles and the Authorization Code + PKCE flow

record_voice_overSay

Four roles, and get the names right because the spec uses them and so does every library's config.

drawBoard / screen
Resource Owner       - you (the human who owns the calendar)
Client                - the travel app (wants access)
Authorization Server  - Google's login/consent system (issues tokens)
Resource Server       - Google Calendar's API (actually holds the data)
record_voice_overSay

Client wants data. Resource Server holds the data. Authorization Server is the gatekeeper the Resource Owner trusts to grant access. Client never talks to the Resource Owner's password — it only ever gets a token from the Authorization Server, after the Resource Owner explicitly approves.

drawBoard — diagram
sequenceDiagram participant U as User (Resource Owner) participant C as Client (Travel App) participant AS as Authorization Server (Google) participant RS as Resource Server (Calendar API) C->>C: generate code_verifier (random), code_challenge = SHA256(code_verifier) C->>U: redirect to AS /authorize?client_id&redirect_uri&scope&state&code_challenge U->>AS: logs in, approves scope ("view your calendar") AS->>C: redirect to redirect_uri with ?code=abc123&state=... C->>C: verify state matches what it sent C->>AS: POST /token { code, code_verifier, client_id, redirect_uri } AS->>AS: check code_verifier hashes to the stored code_challenge AS->>C: access_token (+ refresh_token, + id_token) C->>RS: GET /calendar/events Authorization: Bearer access_token RS->>C: calendar data
record_voice_overSay

Step one: before anything happens over the network, the Client makes up a random string, code_verifier, and keeps it to itself. It hashes that string to get code_challenge. Only the hash goes out over the network at this point.

record_voice_overSay

Step two: Client redirects the user's browser to Google's /authorize endpoint, sending client_id — which app this is — redirect_uri — where to send the user back — scope — what access is being requested, like calendar.readonly — state, a random value the Client will check later — and code_challenge.

record_voice_overSay

Step three: the user is now looking at Google's login page, not the travel app's. They log in — if they aren't already — and see a consent screen: 'Travel App wants to view your calendar. Allow?' That screen is the entire point of this exercise. The user is granting one narrow scope, on Google's own turf, never typing their password into the travel app.

record_voice_overSay

Step four: Google redirects back to the redirect_uri the Client gave it, with a short-lived, single-use code and the same state value it received.

quizAsk the room

Why does the Client bother checking that state matches what it originally sent?

Expected answer

So it knows the redirect actually came from a flow it started.

If stuck: imagine an attacker tricks your browser into hitting your app's callback URL with a code the attacker got from their own login. Without state, your app might accept that code as if it were yours. state is a nonce your app generates and later re-checks — it ties the response to the exact request that started it, which is what stops that class of forgery. This is a CSRF-style defense, specific to this flow.

record_voice_overSay

Step five: Client takes that code, along with its original code_verifier — the one it never sent over the network — and POSTs both to Google's /token endpoint.

record_voice_overSay

Step six, the important one: Google hashes the code_verifier it just received and checks that it matches the code_challenge it was given all the way back in step two.

quizAsk the room

What attack does that check actually block? Assume an attacker managed to intercept the authorization code in step four — maybe through a badly configured redirect, or a malicious app on the same device intercepting the callback. Can they use that stolen code?

Expected answer

No — they don't have the code_verifier, only the Client does, and it was never sent over the network until step five.

This is exactly why PKCE — Proof Key for Code Exchange — exists. It was added to the spec specifically for clients that can't hold a secret safely: mobile apps and single-page JavaScript apps, where anyone can decompile the APK or read the JS. There's no client_secret protecting this flow the way there is for a traditional server-side web app; PKCE's verifier/challenge pair plays that role instead, proving that whoever is redeeming the code is the same party who started the flow — without ever needing a secret a mobile app can't actually keep secret.

record_voice_overSay

Step seven: Google issues an access_token. Often also a refresh_token — same pattern as before, so the Client doesn't need the user to re-consent every 15 minutes. And, if this app also asked for the openid scope, an id_token too — hold that thought, it's the whole answer to our next question.

record_voice_overSay

Step eight: Client calls the Calendar API — the Resource Server — with Authorization: Bearer <access_token>. Resource Server validates it and returns data. Notice: this last step is identical to what we built with our own JWTs an hour ago. That's not a coincidence — Google's access tokens often are JWTs, or the Resource Server treats opaque tokens the same way by checking with the Authorization Server. Same shape, same idea: bearer token in a header, verified, request proceeds.

helpIf they're stuck

If the whole flow feels like too many hops, compress it to one sentence and rebuild from there: 'The Client never sees the password. It gets a one-time code by asking the user to approve something on Google's turf, trades that code for a token by proving it's the same Client that asked, and then uses that token like any other bearer token.' Every step beyond that sentence exists to close one specific way of cheating this handoff — which is exactly what we just walked through, one attack at a time.

Segment 9 · 01:29–01:36

Misconception check

Is OAuth2 how "login with Google" works?

record_voice_overSay

I said a few minutes ago: OAuth2 is not a login system. But you've absolutely used 'Log in with Google' buttons. So what's actually happening there?

quizAsk the room

In the flow we just drew, is there anything that tells the Client who the user is — a name, an email? Look at what actually came back in step seven.

Expected answer

Not really — just an access token that lets you call the Calendar API. That doesn't say who the user is.

Common wrong answer

The access_token tells you.

Does it, though? An access token is scoped to do things — call this API, with this permission. It's an authorization artifact. It doesn't inherently carry 'this is Jane Doe, email jane@x.com.' That's a different job.

record_voice_overSay

That different job is what OpenID Connect — OIDC — adds on top of OAuth2. OIDC is a thin identity layer built on the same flow: if the Client asks for the openid scope, the token response includes one more thing — an id_token, which is a JWT, signed by the Authorization Server, whose payload actually says 'this user's ID is X, name is Y, email is Z.' That's what login-with-Google actually is: an OAuth2 flow, run specifically to get an OIDC id_token, which your app then reads as a signed statement of identity — the same JWT-verification trick from an hour ago, just issued by Google instead of by you.

drawBoard / screen
access_token -> "you may call this API, with this scope"   (authorization)
id_token     -> "this person is who they say they are"      (authentication - OIDC only)

OAuth2 alone: authorization framework
OAuth2 + OIDC ("openid" scope): also gives you authentication
record_voice_overSay

So the misconception to leave behind: 'OAuth2 is a login protocol' is wrong on its own — OAuth2 is about delegated access to resources. 'Login with Google' works because of OIDC riding on top of OAuth2, producing an identity token. People say 'OAuth login' constantly and it's technically imprecise, but now you know what's actually different underneath, and you'll recognize id_token vs access_token in any real config instead of treating them as interchangeable — they are not, and using one where the other belongs is a real bug, not just sloppy naming.

record_voice_overSay

One more grant type worth knowing exists, in one sentence: Client Credentials — no user involved at all, just one service authenticating to another as itself, common for service-to-service calls. And two you should recognize as dead: Implicit grant, which returned tokens directly in a URL fragment with no code-exchange step and is deprecated because that's a much easier token to leak; and the Password grant, which asked users to type their password directly into the Client — the exact naive approach we opened this section by rejecting. If you see either in a codebase, that's a flag, not a pattern to copy.

Segment 10 · 01:36–01:52

Live code

Wiring this into Spring Security

record_voice_overSay

Let's make our original endpoint actually enforce everything we just talked about. Two separate configurations, because they solve two separate problems — don't merge them in your head.

record_voice_overSay

First: our own login, issuing our own JWTs, the way we built in Segment 4. This is the 'resource server' side — we're the ones who issued the token, so we just need to verify it on every request.

codeCode — live
JwtAuthFilter.java
public class JwtAuthFilter extends OncePerRequestFilter {

    private final JwtUtil jwtUtil;

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                     HttpServletResponse res,
                                     FilterChain chain) throws ServletException, IOException {
        String header = req.getHeader("Authorization");

        if (header != null && header.startsWith("Bearer ")) {
            String token = header.substring(7);
            try {
                Claims claims = jwtUtil.validateAndParse(token);
                List<SimpleGrantedAuthority> authorities = ((List<String>) claims.get("roles"))
                    .stream()
                    .map(role -> new SimpleGrantedAuthority("ROLE_" + role))
                    .toList();

                var auth = new UsernamePasswordAuthenticationToken(
                    claims.getSubject(), null, authorities);
                SecurityContextHolder.getContext().setAuthentication(auth);
            } catch (JwtException e) {
                // bad signature or expired - leave SecurityContext empty.
                // Don't throw here; let the request continue as anonymous
                // and let the filter chain below decide what's allowed.
            }
        }
        chain.doFilter(req, res);
    }
}

Pause on the catch block — this is a spot people get wrong.

record_voice_overSay

This is a spot people get wrong: don't throw an exception here just because the token is bad. If you throw, you've made this filter the thing deciding what's allowed — but that's not its job, that's authorization's job, which happens next. This filter's only job is authentication: figure out who's asking, if anyone. If the token's invalid, that just means 'we don't know who this is' — treat them as anonymous and let the actual authorization rules below decide whether an anonymous request is even allowed to proceed.

codeCode — live
SecurityConfig.java
@Configuration
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http, JwtAuthFilter jwtAuthFilter) throws Exception {
        http
            .csrf(csrf -> csrf.disable()) // no cookies here, no CSRF surface - safe for a pure bearer-token API
            .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/login").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}

Pause on SessionCreationPolicy.STATELESS — this is us telling Spring not to secretly create an HttpSession.

quizAsk the room

Given what we said about 401 vs 403 — where in this config does each one actually get decided?

Expected answer

401 comes from the filter — if there's no valid token, nobody gets set as authenticated. 403 comes from authorizeHttpRequests — you're authenticated, but hasRole('ADMIN') says no.

Exactly — and that's why the filter never throws on a bad token. It just leaves you unauthenticated, and anyRequest().authenticated() is what turns 'nobody authenticated' into a 401. Two different lines of code, two different questions, matching the distinction from an hour and a half ago.

codeCode — live
UserController.java
@RestController
@RequestMapping("/users")
public class UserController {

    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id, Authentication auth) {
        boolean isSelf = auth.getName().equals(id.toString());
        boolean isAdmin = auth.getAuthorities().stream()
            .anyMatch(a -> a.getAuthority().equals("ROLE_ADMIN"));
        if (!isSelf && !isAdmin) {
            throw new AccessDeniedException("Not allowed to view this user");
        }
        return userRepository.findById(id);
    }

    @DeleteMapping("/admin/users/{id}")
    @PreAuthorize("hasRole('ADMIN')")
    public ResponseEntity<Void> deleteUser(@PathVariable Long id) {
        userRepository.deleteById(id);
        return ResponseEntity.noContent().build();
    }
}

Two different authorization styles, on purpose — annotation for a simple rule, an if-statement for a real one.

record_voice_overSay

Two different authorization styles on purpose. deleteUser is a simple case — only admins, ever — so @PreAuthorize with a role check is enough, declared right on the method, easy to read. getUser is a more common real case: the rule isn't just a role, it's 'you can see your own data, or an admin can see anyone's' — that needs actual logic, so it lives in the method body instead of being squeezed into an annotation expression. Don't force every rule into @PreAuthorize just because it's tidy; sometimes an if statement is the more honest, more readable choice.

helpIf they're stuck

If the two configs feel like they contradict each other — 'wait, are we the resource server or the client now?' — name it directly: we are two different roles depending on the config. In the first block, we issued the JWT, so we're validating our own tokens — acting as a Resource Server for tokens we ourselves minted. In the second block, Google issues the token, and we're the ones receiving it to log a user in — we're acting as an OAuth2 Client. Same underlying mechanism, bearer token in a header, verified by signature — different party doing the issuing.

The gotchas, as a checklist

record_voice_overSay

Fast recap, as a list of things that will actually bite you, because that's more useful right now than re-deriving everything.

  • closeTreating a 401 and a 403 as interchangeable — they answer different questions
  • closeThinking base64 = encryption — JWT payloads are readable by anyone, just not fake-able
  • closeStoring a JWT in localStorage without weighing it against the httpOnly-cookie / CSRF tradeoff
  • closeAssuming a leaked JWT can be revoked like a session — it can't; short expiry + refresh is the mitigation
  • closeCalling "login with Google" an OAuth2 feature — it's OIDC (the openid scope) riding on OAuth2
  • closeForgetting the "openid" scope and then wondering why there's no user identity available
  • closeUsing the Implicit or Password grant because an old tutorial showed it — both are deprecated for good reasons
  • closeThrowing inside the JWT filter on a bad token instead of just leaving the request unauthenticated
record_voice_overSay

If you remember nothing else from two hours: authentication and authorization are different questions, JWT trades a database lookup for the inability to instantly revoke, and OAuth2 is about delegated access — the login experience you're used to is OIDC borrowing that mechanism, not OAuth2 doing it alone.
